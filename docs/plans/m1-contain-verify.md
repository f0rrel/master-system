# Milestone 1 plan: Contain and verify

| | |
| --- | --- |
| Status | **Waiting for owner approval.** No code is written until the owner approves. |
| Branch | `m1-contain-verify` (from `claude-week` `dab0928`) |

Objective (README §12): a worktree per attempt; the lock held by the worker
process; frozen acceptance criteria checked by a verifier the orchestrator owns;
evidence bound to the spec hash and SHAs; per-attempt deadlines; runtime state
outside every workspace.

Out of scope: containers, parallel attempts, automatic merging, the approval
round-trip (M3), policy by transition (M3), the attempt-budget change (M3),
DBOS (M4), the run CLI (M2), new workers.

## 1. Concrete problems found in the given decisions

Each of these changes a decision slightly. They are listed first so the owner can
reject them before reading the rest.

| # | Decision | Problem | What this plan does instead |
| --- | --- | --- | --- |
| P1 | 3: history and sessions under `$XDG_DATA_HOME/master-system/`; refuse any workspace inside the state directory | If worktrees also live under `master-system/`, every worktree sits inside the state directory and would be refused. | State directory = `$XDG_DATA_HOME/master-system/` (history + sessions). Worktrees root = a **sibling**, `$XDG_DATA_HOME/master-system-worktrees/`. Both configurable. The worktrees root itself is checked against the protected paths when constructed. |
| P2 | 4: the shared helper "enforces the deadline by killing the group" | The loop enforces the deadline. If the loop is `kill -9`ed, nothing enforces it any more, and an orphaned worker holds the inherited lock **forever**. | The helper launches the worker under coreutils `timeout --kill-after=<grace> <secs>`, which runs in the worker's process group and kills the whole group at the deadline even if the loop is dead. The helper also kills the group itself (belt and braces). `timeout` is part of coreutils, which every Linux has; no Python dependency is added. **Verified:** with the loop SIGKILLed, `timeout --kill-after=1s 2s sh -c 'sleep 30 & sleep 30'` killed both the worker and its grandchild at the deadline. |
| P3 | 1: "records base_sha in attempt_started"; worktree path is `<root>/<project>/<attempt_id>` | `attempt_id` is generated by the history store **inside** `append`, so the path is unknown until after the event is written, and writing the worktree path afterwards would break "intent before side effect". | The orchestrator generates the attempt id (uuid4 hex) and passes it to `append` as `event_id` for `attempt_started`; the store still enforces uniqueness and that `attempt_id == event_id`. `attempt_started` then records base_sha, worktree path and branch **before** `git worktree add` runs. |
| P4 | 1 + 9: the human CLI "merges result_sha into base_branch" | A real merge can conflict and needs judgement; also, if `base_branch` is checked out in the owner's main checkout, updating it must keep that checkout's working tree consistent. | **Fast-forward only.** If `base_branch` is an ancestor of `result_sha`, advance it (`git merge --ff-only` in the worktree that has it checked out, refused if that checkout is dirty; otherwise `git update-ref` with the expected old value). If the base moved on, refuse ("re-run the task on the new base"). Idempotent: if `result_sha` is already reachable from `base_branch`, it is a no-op and records nothing new. |
| P5 | 10: recovery "on every lock acquisition" | `core/master.py` and `reason_cli` take the lock too, but `master.py` may not import history, sqlite or subprocess (pinned by tests), and their writes do not depend on closed-out records. | Recovery runs on every lock acquisition **by a history user**: `SessionRunner` (start and resume), the loop when it takes the lock itself, and the integrate command. The two human state CLIs do not run it. |
| P6 | 8: re-titling invalidates a pass | `update_task(task_id, title="X", status="completed")` would be compared against the *current* title and pass the gate. | The gate compares the latest attempt's `spec_hash` with the spec **after** the operation is applied (current task with the operation's `title` merged in). |
| P7 | README §12 acceptance "re-titling **or reopening** invalidates a pass" vs. the brief "re-titling or changing acceptance" | Reopening does not change the spec, so spec_hash cannot detect it. Detecting it needs transition history and policy by transition (H2, M4), both Milestone 3. | Follow the brief. README §12's criterion is reworded to "re-titling a task or changing its acceptance", and "a reopen requires a human" is added to Milestone 3's acceptance (it is already covered by H2 there). |
| P8 | 4 + 5: one deadline per attempt | Acceptance commands also need a bound, and they run after the worker. | The worker gets the attempt deadline. Verification gets its own deadline (default 30 min total, 10 min per command), recorded in the verification event. Both use the same helper and the same lock fd. |

Cancel (decision 5): **not included.** A cheap cancel would kill a pgid read from
history, and if the worker already exited and the pid was reused, it would kill an
unrelated process. With deadlines enforced by `timeout` (P2), a stuck worker ends on
its own. Cancel goes to the remaining-work list (DBOS cancel, Milestone 4).

## 2. Design

### 2.1 Runtime paths (`core/paths.py`, new)

```python
RuntimePaths(state_dir, worktrees_root)          # frozen dataclass
RuntimePaths.default(env=os.environ)             # XDG_DATA_HOME or ~/.local/share
  .history_path  -> state_dir / "history.sqlite"
  .sessions_dir  -> state_dir / "sessions"
```

- `SQLiteHistoryStore()` and `FileSessionStore()` default to `RuntimePaths.default()`.
  Both still accept explicit paths, and every test passes one.
- `SessionRunner(..., paths=None)` uses the defaults for whatever store or
  history it has to create.
- SQLite: `sqlite3.connect(..., timeout=5.0)` and `PRAGMA busy_timeout=5000`.
- The constants `DEFAULT_SESSIONS_ROOT` and `DEFAULT_HISTORY_PATH` (inside the repo)
  are removed.

### 2.2 Isolation rule (`core/workspace.py`)

`check_isolated(path, protected)` resolves symlinks with `Path.resolve()` and
refuses if `path` equals, contains, or sits inside any protected path.

The protected paths are:
- the projects root (`master.root`);
- the state directory;
- the control-plane source directory (the directory that contains `core/`).

The third is an addition beyond the brief. It enforces "do not point a project at
this repository" in code, not only by convention, and it is consistent with
"stop self-hosting until Milestone 3".

The rule is checked:
- against the project's `repository` and the worktrees root, before any attempt;
- against each new worktree path, after it is computed.

A violation is a `run_task` refusal (`workspace_refused`), not an attempt.

### 2.3 Project repository (`project.yaml`)

New optional keys, validated by `ProjectState._check` (shape only, no filesystem access):

```yaml
repository: /home/owner/code/toy-repo   # absolute path (after ~ expansion), a git repo
base_branch: main                        # required if repository is set
```

A project without `repository` cannot run attempts. `run_task` is refused with
`no_repository`. `projects/ai-system` stays without one.

### 2.4 Attempt workspace (`core/workspace.py`, new)

`GitWorktrees(worktrees_root, protected)` is the orchestrator's git helper. It
uses git through `subprocess` and adds no dependencies. Every call uses
`git -C <dir>` with `GIT_TERMINAL_PROMPT=0`.

| Method | git |
| --- | --- |
| `check_repository(repo, base_branch) -> base_sha` | `rev-parse --show-toplevel`, `rev-parse --verify <base>^{commit}` |
| `create(repo, project_id, attempt_id, base_sha) -> path` | `worktree add <root>/<project>/<attempt_id> -b attempt/<attempt_id> <base_sha>` |
| `snapshot(path, base_sha) -> facts` | `add -A`; `-c user.name=master-system -c user.email=master-system@localhost -c commit.gpgsign=false commit --no-verify -m "attempt <id>"` if anything is staged; then `rev-parse HEAD`, `diff --numstat --no-renames base..HEAD`, `diff --name-only --no-renames base..HEAD` |
| `observe(path, base_sha) -> facts` | read-only: `status --porcelain`, `diff --numstat base` (no commit; used by recovery) |

- Worktrees and `attempt/*` branches are **kept**. Cleanup is a later command.
- If the worker committed on its own branch, those commits are included in
  `base..HEAD`. If it moved HEAD somewhere else, the diff shows exactly what is
  there now. Either way the facts come from git, not from the worker.
- `files_changed` is capped at 200 paths, plus a count of the rest.
- The commit identity and `--no-verify` are deliberate: snapshot commits must not
  run the managed repo's hooks, and must not depend on the owner's signing setup.

`AttemptWorkspace` (frozen dataclass) is what workers and verifiers receive:

```python
AttemptWorkspace(path, base_sha, result_sha=None, deadline=<monotonic>, deadline_at=<ISO>,
                 lock_fd=<int|None>, on_spawn=<callback>)
  .remaining() -> seconds
  .run(argv, *, timeout=None, env=None) -> ProcessOutcome   # the only way to start a process
```

### 2.5 Shared worker process helper (`core/worker_process.py`, new)

`run_process(argv, *, cwd, deadline, lock_fd, grace=10, env=None) -> ProcessOutcome`
- Launches `["timeout", f"--kill-after={grace}s", f"{secs}s", *argv]` with:
  - `start_new_session=True` (a new process group and session);
  - `pass_fds=(lock_fd,)` when there is a lock;
  - stdout and stderr captured;
  - stdin set to `DEVNULL`.
- Calls `on_spawn(pid, pgid)` immediately after spawn. The orchestrator turns that
  into an `attempt_process` event, so the pid and pgid are in history even if the
  loop dies.
- On its own deadline it does `killpg(SIGTERM)`, waits `grace`, then `killpg(SIGKILL)`.
- Returns `ProcessOutcome(returncode, stdout, stderr, timed_out, pid, pgid)`.
  - `timed_out` is true if the helper killed the group, or if the exit status is
    `timeout`'s 124 or 137.

`ProjectLock.fileno()` is added so the lock's fd can be passed.

**Boundary test (new):** no backend or verifier module imports `subprocess`. All
process launches go through `AttemptWorkspace.run`.

### 2.6 Backends and verifiers receive the workspace

```python
ExecutionBackend.execute(task, context, *, workspace: AttemptWorkspace) -> ExecutionResult
VerificationBackend.verify(task, context, evidence=None, *, workspace: AttemptWorkspace) -> VerificationResult
```

- **OpenCode backend.** The `workdir` and `timeout` constructor arguments are removed.
  It runs `opencode run --dir <workspace.path> ...` through `workspace.run`.
  `timed_out` maps to `failed` with a neutral reason. The deadline is the only
  time bound.
- **Ollama backend.** The `workdir` argument and `_resolve_workdir` (which made a
  temp dir) are removed. Tools are confined to `workspace.path`. The deadline is
  checked before every turn, and each HTTP timeout is `min(self._timeout, workspace.remaining())`.
  When the deadline passes it returns `failed` ("deadline reached").
- **Nothing reads a path from worker artifacts.**
  - The orchestrator no longer passes worker artifacts to the verifier. Its
    `evidence` argument now carries orchestrator-observed facts:
    base/result SHA, files changed, diff stats, outcome.
  - Worker artifacts go to history only.

### 2.7 Orchestrated attempt, in order

The loop's `run_task` precheck (refusals, no attempt counted):
- task executable (existing);
- attempt limit (existing);
- `no_repository`, `workspace_refused`;
- `repository_unusable`: not a git repo, or the base branch doesn't resolve.

Then the orchestrator:

1. `attempt_id = uuid4().hex`; compute the worktree path; isolation check on it.
2. **append `attempt_started`**: `step`, `worker`, `repository`, `base_branch`,
   `base_sha`, `worktree`, `branch`, `spec_hash`, `timeout_s`, `deadline_at`.
3. `git worktree add`. If it fails: `attempt_finished{outcome: "error", error_type: "WorkspaceError"}`, then re-raise (`run_error`).
4. The worker runs with `workspace=AttemptWorkspace(...)`. Each process spawn
   appends **`attempt_process`** (`phase: "worker"`, `pid`, `pgid`, `deadline_at`).
5. Whether the worker returned, raised or timed out: `snapshot` (commit), then
   **append `attempt_finished`** with:
   - `outcome`, decided by the orchestrator: `finished`, `timed_out` or `error`;
   - `worker_reported_status`, `reason`, `artifacts`, `state_updates`, `worker`;
   - `processes`: `[{pid, pgid, returncode, timed_out}]`;
   - `result_sha`, `files_changed`, `files_changed_count`, `diffstat`: `{files, insertions, deletions}`;
   - `snapshot_error` (if the commit itself failed).

   `timed_out` means a helper reported it, or the wall clock passed the deadline
   when the worker returned. If the worker raised, the exception is re-raised
   after this event.
6. If the outcome is `finished`: verify with a fresh `AttemptWorkspace`
   (`result_sha` set, verification deadline). Verification processes are recorded
   as `attempt_process{phase: "verification"}`. Then **append `verification`**
   (unchanged fields, plus `deadline_at`).

   If the outcome is `timed_out`, verification is skipped. The evidence shows no
   verification, and the gate refuses anyway.

### 2.8 Acceptance (`tasks.yaml`)

```yaml
- id: t1
  title: Add greet()
  acceptance:
    commands: ["python -m pytest -q tests/test_greet.py"]   # >= 1 non-empty string
    protected_paths: ["tests/*", "conftest.py"]             # optional; relative globs
```

**Validation (ProjectState):**
- `acceptance` is a mapping with only these keys;
- `commands` is a non-empty list of non-empty strings;
- `protected_paths` is a list of non-empty strings that are neither absolute nor
  contain `..`.

**Glob semantics:** `fnmatch.fnmatchcase` on repo-relative POSIX paths, so `*`
also crosses `/`. `tests/*` therefore protects everything under `tests/`.

**Who can set it:**
- **Humans only**, through `python -m core.master set-acceptance <project> <task> --command ... [--command ...] [--protect GLOB ...]`
  or `--clear`, or by editing the YAML. The command takes the project lock.
- Implemented as `Master.set_task_acceptance()` → `WorkManager.set_task_acceptance()`.
- Not in `SPECS`. Not in `MUTABLE_TASK_FIELDS`, so a model's
  `update_task(acceptance=...)` is rejected by the domain layer, as any unknown
  field is today. `create_task` is not variadic, so it rejects the field too.

**Who sees it:**
- Master sees `has_acceptance: true|false` per task. This is conservative: the
  commands are not put into the prompt.
- The worker receives the task record, which includes `acceptance`, so it knows
  what "done" means.

### 2.9 AcceptanceVerifier (`core/acceptance_verifier.py`, new)

1. No acceptance → `unable_to_verify`.
2. `git status --porcelain` in the worktree is not clean → `unable_to_verify`
   (something is still writing).
3. `git diff --name-only --no-renames base_sha result_sha`. Any path matching a
   protected glob → `fail`, with a finding `{kind: "protected_path", path}`.
   Commands still run, for information.
4. Each command runs as `["/bin/sh", "-c", cmd]` through `workspace.run`, with a
   per-command timeout of `min(600 s, remaining)`. Every command runs, even after
   a failure. Each failure is a finding:
   `{kind: "command_failed", command, exit_code, timed_out, output_excerpt}`.
   The excerpt is the last 2,000 characters of stdout+stderr.
5. The verdict is `pass` only if nothing was protected and every command exited 0.
   Otherwise it is `fail`.
6. `evidence`: `{base_sha, result_sha, commands_run, protected_violations}`.
   Nothing comes from worker artifacts.

### 2.10 Evidence binding and context (`core/evidence.py`)

- `spec_hash(task) = sha256(json.dumps({"title": ..., "acceptance": ... or None}, sort_keys=True, separators=(",", ":")))`,
  in `core/evidence.py`.
- Gate order:
  1. `no_attempt`
  2. `latest_attempt_interrupted` / `_unfinished` / `_errored` / **`_timed_out`**
  3. **`spec_changed`**: the latest attempt's `spec_hash` is missing (an older
     event) or differs from the spec after the operation (P6)
  4. `not_verified`, `verification_errored`, `verification_<verdict>`
- **Item 11 (included, small).** `latest_attempt` in Master's context becomes:
  - `outcome` (`finished`, `timed_out`, `error`, `interrupted` or `unfinished`, decided by the orchestrator);
  - `worker_reported_status` (the worker's claim, labelled as such);
  - `changes`: `{files, insertions, deletions}`;
  - `verification` (unchanged);
  - `spec_current` (bool).
- **Legacy events.** An `attempt_finished` without `outcome` maps to outcome
  `error` if its `status` is `error`, otherwise `finished`. Its
  `worker_reported_status` is its old `status`.
- **The loop** passes the current task record to the gate. The engine adds
  `has_acceptance` to each task in the context.

### 2.11 Project-wide recovery (`core/recovery.py`, new; moved out of `session_runner.py`)

`recover_project(history, store, project_id, workspaces)` runs while the lock is held:
- every run of the project, whether in a session or not, without a recorded end
  gets `run_interrupted`;
- every attempt without an outcome gets `attempt_interrupted`, now carrying
  `worktree_present` and `git_status` (porcelain lines, capped at 200), plus
  `diffstat` and `untracked` against `base_sha`, from `observe` (read-only);
- every session of the project in `RUNNING` is stopped with `interrupted`, and its
  steps are counted from history (as today).

It runs in:
- `SessionRunner.start` and `resume`;
- `AutonomousLoop.run` when the loop takes the lock itself;
- the integrate command.

**Locking for direct loop use.** `AutonomousLoop` gains `lock=None`. If no lock is
given, `run()` takes the `ProjectLock` itself and holds it for the run (and
recovers first). `SessionRunner` passes the lock it holds. So every autonomous run
holds the lock, and every worker inherits it.

### 2.12 INTEGRATE

**The operation:**
- `OperationKind.INTEGRATE`, with `integrate_attempt(project_id, task_id, attempt_id)` at impact `CRITICAL`.
- `requires_approval` is true, so the loop stops with `approval_required (policy)`.
- `ReasoningInterface.execute` refuses it with the new `RequestError.HUMAN_ONLY`,
  so an approved proposal in `reason_cli` cannot run it either. The message points
  to the CLI.

**The human command** is `python -m core.attempts integrate <project_id> <attempt_id>`,
in the new module `core/attempts.py`. `core/master.py` cannot import history or
subprocess, so it cannot live there. Under the project lock (after recovery), it:
1. reads `attempt_started`, `attempt_finished` and `verification` for that attempt
   (all written by the orchestrator);
2. requires:
   - `outcome == finished`;
   - verdict `pass`;
   - `spec_hash` equal to the task's current spec;
   - the attempt's `repository` and `base_branch` still matching `project.yaml`;
3. is idempotent: if `result_sha` is already reachable from `base_branch`, it
   prints "already integrated" and records nothing;
4. fast-forwards only (P4);
5. **appends `integration`** with:
   - `attempt_id`, `task_id`, `repository`, `base_branch`;
   - `previous_sha`, `result_sha`;
   - `method` (`ff_merge` or `update_ref`);
   - `actor: "human-cli"`.

Integration does not change task status.

### 2.13 History schema v2 (data migration)

New event types `attempt_process` and `integration` need the SQLite `CHECK`
constraint widened, so `SCHEMA_VERSION` becomes 2.

On opening a v1 database, `SQLiteHistoryStore` migrates it in one transaction:
1. create `events_v2`;
2. copy every row (`seq` preserved);
3. drop the old table (this also drops its triggers);
4. rename the new table;
5. recreate the indexes and append-only triggers;
6. set the version to 2.

An unknown newer version is still refused. Payload changes need no migration,
because evidence reads both the old and the new shapes (§2.10).

**Other data:**
- Sessions: no schema change.
- `project.yaml` and `tasks.yaml`: new optional keys only.
- Repo-local `sessions/` and `var/history.sqlite` (gitignored, normally absent)
  are **not** moved automatically. README §8 gets the `mv` commands.

## 8. Remaining work after this milestone

- **Not containment, only isolation.** A worker still runs as the owner's user. It
  can write outside its worktree, or change refs in the managed repo, including
  `base_branch`, through git. Worktrees isolate files, not authority; containers
  are a later milestone.
- Cancel is deferred (Milestone 4, DBOS).
- Worktree and branch cleanup.
- Reopen detection (Milestone 3, H2).
- Merges that are not fast-forwards.
